# 后端开发文档（当前实现版）
## 1. 文档目的

本文档用于说明当前后端已经真实落地了什么、代码结构怎么组织、接口和脚本怎么使用、后续如何继续新增功能。

目标不是讲产品方案，而是讲当前仓库里实际可运行的后端实现。

本文档适合这些同事使用：

- 后端开发
- 前端联调
- 测试
- 需要继续扩展当前后端功能的同事

## 2. 当前后端总体架构

当前后端位于：

- [backend](/F:/服装/Fashion-Desgin/backend)

采用双服务 + 共享包结构：

```text
backend/
  apps/
    biz-api/
    ledger-service/
  packages/
    shared-kernel/
    shared-types/
  prisma/
    biz/
    ledger/
  generated/
    biz-client/
    ledger-client/
  scripts/
```

职责划分：

- `biz-api`
  - 主业务 API
  - 当前几乎所有已开发功能都在这里
- `ledger-service`
  - 账务服务占位
  - 当前主要具备基础启动框架
- `shared-kernel`
  - 共享基础能力
- `shared-types`
  - DTO、枚举、共享领域类型

## 7. 当前后端关键实现约定

### 7.1 请求返回格式

当前已统一采用：

成功：

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "request_id": "req_xxx"
}
```

失败：

```json
{
  "code": 400001,
  "message": "TASK_CREATE_FAILED",
  "request_id": "req_xxx"
}
```

当前统一写法来自：

- `writeSuccess`
- `writeError`

位置：

- [json.ts](/F:/服装/Fashion-Desgin/backend/packages/shared-kernel/src/http/json.ts:1)

### 7.2 路由装配方式

当前项目没有引入大型框架路由层，而是在：

- [app.ts](/F:/服装/Fashion-Desgin/backend/apps/biz-api/src/modules/system/app.ts:1)

中直接按路径和方法分发。

优点：

- 简单
- 当前开发阶段改动快

缺点：

- 随接口增多，`app.ts` 会变大

后续如果接口量明显增加，可以考虑在不改业务逻辑的前提下做路由拆分。

### 7.3 任务事件构造方式

当前任务事件统一通过：

- [task-event.factory.ts](/F:/服装/Fashion-Desgin/backend/apps/biz-api/src/modules/tasks/services/task-event.factory.ts:1)

构造。

不要继续在多个 service 里散落手写：

- `event_id`
- `from_status`
- `to_status`
- `occurred_at`

### 7.4 仓储驱动切换

当前仓储驱动由环境变量控制：

- `TASK_REPOSITORY_DRIVER`

可选值：

- `memory`
- `prisma`

当前本地已经默认切到：

- `prisma`

位置：

- [backend/.env](/F:/服装/Fashion-Desgin/backend/.env:1)

## 9. 如何继续新增功能

### 9.1 新增普通业务接口的推荐步骤

1. 先确认功能属于哪个模块
   - `tasks`
   - `workbench`
   - `realtime`
   - 未来新模块
2. 如果涉及新字段，先改 Prisma schema 和 shared-types DTO
3. 如果涉及任务事实，优先复用 `generation_tasks` / `task_events`
4. 在 service 中实现业务逻辑
5. 在 controller 中接入
6. 在 `app.ts` 挂路由
7. 补一个最小验收脚本
8. 运行 `npm run build` 和相关验收脚本

### 9.2 如果要新增一个新页面模块

推荐结构：

```text
backend/apps/biz-api/src/modules/new-module/
  controllers/
  services/
```

新增模块时建议遵循：

- DTO 先放 `shared-types`
- 业务逻辑放 service
- controller 只做参数读取和返回包装
- 如果会复用任务状态，不要重造一套新任务逻辑

### 9.3 如果要扩展工作台

优先方向：

- 真实素材上传链路
- 真实任务输入资产写入
- 真实输出资产写入
- 模型与场景改为真实表

不要优先做的：

- 再做一套新的工作台任务表
- 为每种工作台模式复制一套 controller/service

### 9.4 如果要扩展实时同步

当前后端已经够用，后续更合理的方向是：

- 前端全局任务中心接入
- HTTP fallback 轮询协调
- 多实例广播（Redis Pub/Sub）

如果真的要继续扩后端实时层，优先做：

- token 与真实登录态绑定
- 横向扩展广播
- 连接监控与统计

## 10. 当前后端已知限制

### 10.1 未完成真实上传链路

当前 `assets` 表已落，但上传接口和真实资产写入流程还没完整闭环。

### 10.2 Ledger 仍有 stub

当前 `ledgerClient` 仍是最小占位实现，不是完整的冻结/结算/退款主链路。

### 10.3 工作台目录数据仍是静态目录

模型和场景当前来自：

- [workbench.catalog.ts](/F:/服装/Fashion-Desgin/backend/apps/biz-api/src/modules/workbench/services/workbench.catalog.ts:1)

而不是数据库表。

### 10.4 `app.ts` 会持续变大

当前路由集中在一个入口，适合快速迭代，但后续接口越来越多时需要适度拆分。

## 11. 当前推荐的继续开发顺序

如果后续继续开发，推荐优先级如下：

1. 前端工作台接真实接口
2. 工作台素材上传与真实资产链路
3. 项目页真实后端闭环
4. 账务主链路替换 stub
5. 全局任务中心前端接入

## 12. 给后续开发同事的操作建议

每次改动后，最少执行：

1. `npm run build`
2. 与改动相关的一条验收脚本

如果改动涉及数据库：

1. `npm run prisma:generate`
2. `npm run prisma:push`
3. `npm run db:inspect`

如果改动涉及任务主链路：

1. `npm run api:verify:tasks`
2. `npm run api:verify:lifecycle`

如果改动涉及实时同步：

1. `npm run api:verify:ws`

如果改动涉及工作台：

1. `npm run api:verify:workbench`

## 13. 结论

当前后端已经具备一套可运行、可验证、可扩展的最小业务底座：

- 双数据库
- 任务中心
- 生命周期
- 实时同步
- 工作台基础业务闭环

后续同事应该在这套既有结构之上继续演进，而不是重新拆分另一套平行后端体系。
