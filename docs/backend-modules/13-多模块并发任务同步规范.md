# 多模块并发任务同步规范

## 1. 目标

在现有“WebSocket 主通道 + HTTP 兜底 + 统一任务同步协调器”方案基础上，本项目必须进一步支持同一用户在多个业务模块同时生成图片，并保证状态同步体系在多模块并发场景下仍然稳定、可控、可扩展。

本章节只做增强约束，不替换原文档中的总体结构、主通道策略和轮询兜底策略。

## 2. 基本原则

### 2.1 同一用户支持多模块并发生成

本项目必须支持同一用户同时在多个业务模块发起图片生成任务，例如：

- AI 在线生成工作台
- 创意生图模块
- 视频生成 Beta 中的封面图或相关图片任务
- 后续扩展的其他图片生成模块

系统必须保证这些任务可以同时存在、同时运行、同时更新，不因模块不同而相互覆盖或串线。

### 2.2 所有图片生成模块共享同一套全局任务中心

所有图片生成模块必须共享同一套全局任务中心，不允许：

- 每个模块维护独立的任务实时同步实现
- 每个模块各自定义 WebSocket 协议
- 每个模块各自维护自己的轮询器、重连器、去重器

正确做法是：

- 所有模块统一接入全局任务中心
- 任务中心统一管理连接、重连、轮询、状态合并、去重、乱序保护
- 模块只按条件订阅自己关心的任务集合

### 2.3 前端全局只允许一条主 WebSocket 连接

前端全局只允许维护一条主 WebSocket 连接，用于接收当前用户全部任务事件。

不允许的做法：

- 工作台页面开一条 WebSocket
- 项目页再开一条 WebSocket
- 创意页再开一条 WebSocket
- 弹窗或抽屉再单独开一条 WebSocket

允许的做法：

- 应用级任务中心在全局维持一条主连接
- 多个页面和模块共享这条连接
- 通过任务归属字段在前端做分发

### 2.4 模块只负责订阅，不负责同步实现

业务模块只负责表达“我关心哪些任务”，不负责以下能力：

- 建立连接
- 连接重试
- fallback 轮询
- 事件去重
- 状态合并
- 乱序保护
- 终态停止
- 页面切后台降频
- 页面恢复后的 resync

这些能力必须全部收敛在全局任务中心中。

## 3. 多模块任务中心架构

### 3.1 架构定位

前端必须引入统一的全局任务中心，例如：

- `globalTaskCenter`
- `taskSyncCoordinator`
- `taskRealtimeManager`

其定位是应用级基础设施，而不是某个页面的局部 Hook。

### 3.2 任务中心职责

全局任务中心统一负责：

- 维护唯一主 WebSocket 连接
- 接收并分发所有任务事件
- 管理 fallback 轮询
- 按 `task.id` 合并任务状态
- 按 `version` 和 `updated_at` 做乱序保护
- 按模块、项目、批次建立索引
- 维护运行中任务集合
- 维护最近完成任务集合
- 为各业务模块提供只读订阅能力

### 3.3 模块接入方式

模块只能通过注册订阅条件接入任务中心，例如：

- 按 `module` 订阅
- 按 `project_id` 订阅
- 按 `batch_id` 订阅
- 按 `task_type` 订阅
- 按显式 `task_id` 集合订阅

模块拿到的是“过滤后的任务视图”，而不是直接操作底层连接。

## 4. 任务 DTO 增强规范

为支持多模块并发任务同步，任务 DTO 必须补充以下字段。

### 4.1 必填增强字段

- `module`
- `scene`
- `task_type`
- `project_id`
- `batch_id`
- `source_page`

### 4.2 字段说明

| 字段 | 类型 | 是否必填 | 说明 |
|---|---|---|---|
| `module` | string | 是 | 模块归属，例如 `ai_generate`、`creative`、`video_beta` |
| `scene` | string \| null | 否 | 场景标识，便于模块内二级视图区分 |
| `task_type` | string | 是 | 任务类型，例如 `clothes`、`real`、`mannequin`、`model_replace`、`creative`、`video` |
| `project_id` | string \| null | 否 | 所属项目 ID |
| `batch_id` | string \| null | 否 | 同一批次生成请求 ID，用于批量任务聚合 |
| `source_page` | string \| null | 否 | 任务创建来源页面，例如 `/ai-generate/clothes` |

### 4.3 设计要求

- `module` 必须是前后端约定的稳定枚举，不允许使用纯展示文案
- `task_type` 描述业务任务类型，`module` 描述功能归属，两者不能混用
- `batch_id` 必须能把一次批量操作下的多个任务归到一起
- `source_page` 用于前端回溯来源，不作为权限判断依据

## 5. WebSocket 事件增强规范

### 5.1 task 对象必须带模块归属信息

WebSocket 事件中的 `task` 对象必须包含完整模块归属字段，至少包括：

- `id`
- `module`
- `task_type`
- `project_id`
- `batch_id`
- `source_page`
- `status`
- `billing_status`
- `progress`
- `stage`
- `updated_at`
- `version`

### 5.2 事件示例

```json
{
  "event_id": "evt_01J...",
  "event_type": "task.updated",
  "occurred_at": "2026-06-10T15:12:31+08:00",
  "task": {
    "id": "tsk_01J...",
    "module": "ai_generate",
    "scene": "clothes_workspace",
    "task_type": "clothes",
    "project_id": "prj_01J...",
    "batch_id": "bat_01J...",
    "source_page": "/ai-generate/clothes",
    "status": "processing",
    "billing_status": "frozen",
    "progress": 63,
    "stage": "rendering",
    "updated_at": "2026-06-10T15:12:31+08:00",
    "version": 12
  }
}
```

### 5.3 分发原则

前端收到事件后，必须先进入全局任务中心，再由任务中心基于以下字段做分发：

- `module`
- `project_id`
- `batch_id`
- `task_type`
- `task.id`

不允许由页面直接消费原始 WebSocket 消息后自行判断归属。

## 6. 前端状态管理增强规范

全局任务中心的状态管理必须至少支持以下结构。

### 6.1 核心索引结构

- `taskMap`
- `taskIdsByModule`
- `taskIdsByProject`
- `taskIdsByBatch`
- `runningTaskIds`
- `recentCompletedTaskIds`

### 6.2 字段定义建议

| 字段 | 类型 | 说明 |
|---|---|---|
| `taskMap` | `Record<string, Task>` | 以 `task.id` 为主键的任务主存储 |
| `taskIdsByModule` | `Record<string, string[]>` | 按模块归档任务 ID |
| `taskIdsByProject` | `Record<string, string[]>` | 按项目归档任务 ID |
| `taskIdsByBatch` | `Record<string, string[]>` | 按批次归档任务 ID |
| `runningTaskIds` | `string[]` | 当前所有非终态任务 ID |
| `recentCompletedTaskIds` | `string[]` | 最近完成任务 ID，按时间倒序维护 |

### 6.3 维护原则

- `taskMap` 是唯一事实源
- 其他结构都是派生索引
- 更新任务时先写 `taskMap`，再更新索引
- 删除或清理任务时必须同步清理索引
- 终态任务从 `runningTaskIds` 中移除
- `recentCompletedTaskIds` 需要有长度上限，例如 50 或 100

## 7. 模块订阅与展示规范

### 7.1 模块只能看到自己关心的任务

模块页面只允许展示符合自己订阅范围的任务：

- 模块页默认按 `module` 过滤
- 项目页默认按 `project_id` 过滤
- 批量结果区默认按 `batch_id` 过滤
- 特定功能面板可按 `task_type` 再做二次过滤

### 7.2 模块不维护独立任务池

不允许出现以下做法：

- 创意模块维护一份自己的 `creativeTaskMap`
- 工作台模块维护一份自己的 `generateTaskMap`
- 项目页再复制一份 `projectTaskMap`

正确做法：

- 所有页面从全局任务中心读取
- 页面只持有筛选条件，不持有独立任务事实副本

### 7.3 页面级视图规则

- 模块页面：只展示本模块任务
- 项目页面：展示该项目下全部任务，可跨模块
- 批次面板：展示该批次下全部任务
- 全局任务中心：展示用户全部运行中任务

## 8. HTTP 查询接口增强规范

### 8.1 列表接口必须支持多维过滤

任务查询接口必须支持以下过滤参数：

- `module`
- `project_id`
- `batch_id`
- `task_type`

建议接口：

- `GET /api/v1/tasks`
- `GET /api/v1/tasks/{id}`

建议查询参数：

- `module`
- `project_id`
- `batch_id`
- `task_type`
- `status`
- `billing_status`
- `page`
- `page_size`

### 8.2 查询使用原则

- 模块页面优先按 `module` 查询
- 项目页优先按 `project_id` 查询
- 批量结果页优先按 `batch_id` 查询
- fallback 轮询时优先使用聚合过滤，不做逐任务暴力详情轮询

### 8.3 禁止事项

- 不允许列表页对每个模块内任务逐条查详情做轮询
- 不允许前端先拉全量任务再自行在浏览器做大规模筛选
- 不允许不带过滤参数地高频拉取整库任务列表

## 9. 多模块并发控制规则

多模块并发场景下，后端必须同时支持三层并发控制。

### 9.1 用户全局并发上限

定义：

- 同一用户在全平台所有模块中的运行中任务总数上限

用途：

- 防止单用户跨多个模块无限提交任务
- 保证整体资源公平使用

建议规则：

- 个人版、基础版、高级版、企业版按套餐不同设置不同全局上限
- 全局上限作用于 `billing_pending`、`queued`、`processing`、`cancelling` 等非终态任务

### 9.2 模块级并发上限

定义：

- 同一用户在某个模块内的并发任务数上限

用途：

- 避免某一个模块独占用户全部配额
- 区分不同模块资源成本

示例：

- `ai_generate` 并发 5
- `creative` 并发 3
- `video_beta` 并发 1

### 9.3 任务类型级并发上限

定义：

- 同一用户在特定 `task_type` 下的运行中任务上限

用途：

- 细化到资源消耗更重的任务类型
- 防止例如高成本 `video` 任务挤占全部资源

示例：

- `clothes` 最多 4
- `real` 最多 4
- `mannequin` 最多 4
- `model_replace` 最多 2
- `creative` 最多 3
- `video` 最多 1

### 9.4 并发校验顺序

创建任务时建议按以下顺序校验：

1. 用户全局并发上限
2. 模块级并发上限
3. 任务类型级并发上限
4. 套餐或权限能力校验
5. 积分余额与报价校验

### 9.5 返回要求

如果触发并发限制，接口应返回明确错误信息，并包含：

- 当前限制维度
- 当前占用数量
- 最大允许数量
- 建议用户操作

例如：

```json
{
  "code": 400103,
  "message": "当前模块并发任务数已达上限",
  "data": {
    "scope": "module",
    "module": "creative",
    "current": 3,
    "limit": 3
  }
}
```

## 10. 多模块场景下的轮询与同步规则补充

### 10.1 轮询仍然是全局任务中心行为

即使在多模块场景下，轮询也仍然只能由全局任务中心发起，不允许模块各自 fallback。

### 10.2 优先按聚合维度轮询

当 `WebSocket` 不可用时，轮询优先级应为：

1. 按 `project_id` 聚合查询
2. 按 `module` 聚合查询
3. 按 `batch_id` 聚合查询
4. 仅在必要时查询单任务详情

### 10.3 多模块同时运行时的轮询限制

- 同一用户同一时刻只允许存在一套 fallback 调度器
- fallback 调度器内部按关注集合聚合请求
- 不因打开多个模块页面而叠加轮询倍数

## 11. 隔离性要求

### 11.1 模块展示隔离

- 创意模块异常，不应影响工作台模块任务展示
- 工作台页面销毁，不应清空全局任务中心中的其他模块任务
- 某一模块视图过滤错误，不应污染 `taskMap` 主存储

### 11.2 状态写入隔离

- 某个模块只读全局任务中心，不直接改写其他模块的筛选结果
- 全局任务中心写入任务时，必须以 `task.id` 为唯一主键，不按模块分库保存

### 11.3 容错原则

- 某个模块 UI 层崩溃，不应影响主 WebSocket 连接
- 某个模块取消订阅后，不应影响其他模块的实时更新
- 单个任务数据异常时，应降级忽略该任务，不应阻断整条事件流

## 12. 验收标准

多模块并发场景下，至少必须满足以下验收要求。

### 12.1 多模块同时生成时状态不串线

验证点：

- 同一用户同时在两个以上模块创建任务
- 各模块只收到并展示符合自己过滤条件的任务
- 不出现 A 模块任务跑到 B 模块页面的情况

### 12.2 不重复建立多条 WebSocket

验证点：

- 用户同时打开多个模块页面
- 前端网络层只存在一条主 WebSocket 连接
- 页面切换不会新增重复连接

### 12.3 模块页面只展示本模块任务

验证点：

- 工作台只展示 `module=ai_generate` 相关任务
- 创意页只展示 `module=creative` 相关任务
- 视频 Beta 页只展示 `module=video_beta` 相关任务

### 12.4 全局任务中心展示所有运行中任务

验证点：

- 全局运行中任务面板可同时看到多个模块的运行中任务
- 可按模块、项目、批次进一步筛选
- 总数与后端运行中任务集合一致

### 12.5 某个模块异常不影响其他模块展示

验证点：

- 人为让某个模块页面发生渲染错误或取消订阅
- 其他模块仍能通过主任务中心持续接收任务更新
- 主 WebSocket 不会因此关闭或重连

### 12.6 fallback 轮询不因多模块而放大

验证点：

- WebSocket 断开后，打开多个模块页面
- 前端仍只存在一套 fallback 调度
- 请求数量按聚合维度控制，不出现倍数增长

## 13. 开发结论

在多模块并发场景下，本项目必须坚持以下强约束：

1. 同一用户可以在多个模块同时生成图片。
2. 所有图片生成模块共享同一套全局任务中心。
3. 前端全局只允许一条主 WebSocket 连接。
4. 模块只做订阅，不做连接、重连、轮询、去重、乱序保护。
5. 任务 DTO 和 WebSocket 事件必须带完整模块归属字段。
6. 任务状态管理必须维护主存储和多维索引。
7. HTTP 查询接口必须支持 `module / project_id / batch_id / task_type` 过滤。
8. 并发控制必须覆盖全局、模块、任务类型三层。
9. 多模块并发验收必须覆盖“不串线、不重复连接、可全局聚合、模块隔离”四类问题。

如果把这套规范落实，后续即使新增更多图片生成模块，也不需要再复制一套任务同步体系，只需要把新模块接入全局任务中心即可。
