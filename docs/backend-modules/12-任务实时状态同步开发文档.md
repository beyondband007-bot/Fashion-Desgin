# 任务实时状态同步开发文档

## 1. 文档目标

本文定义图片生成任务在前后端之间的实时状态同步方案，目标是：

- 明确 `WebSocket` 作为主通道
- 明确接口轮询只作为兜底方案
- 避免“多页面重复轮询、轮询不停止、状态乱序覆盖、终态后继续打接口”这类问题
- 为图片生成工作台、项目页、任务详情页提供统一实时协议

本文不写实现代码，只定义开发规范。

## 2. 背景与问题

你提到二手车项目里“接口轮询太容易出问题”，这类问题通常不是轮询本身，而是轮询没有被约束，常见故障包括：

- 同一个任务被多个组件同时轮询
- 任务已经完成，但轮询没有停止
- 页面切后台后仍然高频轮询
- 轮询结果与 WebSocket 推送相互覆盖
- 网络抖动时重复发起定时器，形成轮询风暴
- 列表页每个任务一条轮询，放大成 N 倍请求
- 后端回调未到达时，前端把短暂中间态误判成失败

因此本项目不采用“纯接口轮询驱动任务状态”的方案，而采用：

- `WebSocket 主通道`
- `HTTP 查询兜底`
- `统一任务同步协调器`

## 3. 设计原则

### 3.1 主原则

- 实时状态以 `WebSocket` 为主
- 轮询只在 `WebSocket` 不可用或短暂失联时启用
- 同一时刻每个任务只能有一个有效同步源
- 终态任务必须立即停止一切同步动作
- 状态更新必须可去重、可排序、可忽略旧事件

### 3.2 不允许的做法

- 不允许每个任务卡片各自启动 `setInterval`
- 不允许列表页对每个运行中任务单独轮询详情接口
- 不允许 WebSocket 正常时继续高频轮询
- 不允许没有页面可见性控制的后台持续轮询
- 不允许前端自行推导扣费、退款、完成状态

## 4. 总体方案

## 4.1 通信结构

```text
Frontend
  -> POST /api/v1/realtime/token
  -> GET /api/v1/ws?token=...
       <- task.created
       <- task.updated
       <- task.completed
       <- task.failed
       <- task.refunded

Fallback
  -> GET /api/v1/tasks/{id}
  -> GET /api/v1/tasks?status=processing,queued...
```

### 4.2 双通道职责

`WebSocket` 负责：

- 进度推送
- 阶段变更
- 完成事件
- 失败事件
- 退款事件

`HTTP` 负责：

- 初次进入页面时拉取当前快照
- WebSocket 断线后的兜底补状态
- 页面重新激活时做一次纠偏
- 疑似漏消息时做强制校准

## 5. 适用页面

统一方案服务于以下页面：

- AI 在线生成工作台
- 我的项目页
- 任务详情页
- 最近结果面板

不同页面只共享同一套同步层，不单独定义各自轮询逻辑。

## 6. 服务端协议定义

### 6.1 获取实时 token

接口：

- `POST /api/v1/realtime/token`

用途：

- 为当前登录用户签发短期 WebSocket token
- token 仅用于建立实时连接，不复用登录 Access Token 直接拼接到 URL

建议返回：

```json
{
  "token": "ws_xxx",
  "expires_in": 300,
  "channel": "user:usr_xxx:tasks"
}
```

### 6.2 WebSocket 建连

接口：

- `GET /api/v1/ws?token={short_lived_ws_token}`

连接要求：

- token 短效
- 服务端校验用户身份
- 一个用户可有多个连接，但要有连接数上限
- 服务端以用户维度推送任务事件

### 6.3 事件模型

事件统一结构建议：

```json
{
  "event_id": "evt_01J...",
  "event_type": "task.updated",
  "occurred_at": "2026-06-10T14:20:31+08:00",
  "task": {
    "id": "tsk_01J...",
    "status": "processing",
    "billing_status": "frozen",
    "progress": 56,
    "stage": "rendering",
    "error_code": null,
    "error_message": null,
    "updated_at": "2026-06-10T14:20:31+08:00",
    "version": 8
  }
}
```

### 6.4 必须字段

每个任务事件必须带：

- `task.id`
- `task.status`
- `task.billing_status`
- `task.progress`
- `task.updated_at`
- `task.version`

原因：

- 前端需要做乱序保护
- 同一个任务的旧事件不能覆盖新状态

### 6.5 事件类型

- `task.created`
- `task.updated`
- `task.completed`
- `task.failed`
- `task.cancelled`
- `task.refunded`

## 7. HTTP 查询接口职责

### 7.1 任务详情查询

接口：

- `GET /api/v1/tasks/{id}`

用途：

- 首次进入任务页时获取完整快照
- WebSocket 断开后的单任务兜底
- 收到异常状态时强制对齐服务端状态

### 7.2 任务列表查询

接口：

- `GET /api/v1/tasks`

用途：

- 项目页或最近结果面板获取任务集合状态
- 页面重新激活时批量纠偏

限制：

- 列表页只允许“聚合轮询列表接口”
- 不允许针对列表内每个任务逐个调用详情接口

## 8. 前端同步架构要求

### 8.1 必须有统一同步协调器

前端必须抽出统一层，例如：

- `taskRealtimeManager`
- 或 `useTaskRealtime`
- 或 `taskSyncCoordinator`

该层统一负责：

- 建立 WebSocket
- 监听事件
- 决定何时轮询
- 合并状态
- 停止终态任务同步

### 8.2 不允许页面各自维护定时器

页面只能订阅状态，不直接创建轮询器。

错误做法：

- `AiGeneratePage` 一个定时器
- `ProjectsPage` 一个定时器
- `RecentResults` 再一个定时器

正确做法：

- 所有页面都向统一协调器注册“我关心哪些任务”
- 协调器决定是否启用 WebSocket 或 HTTP fallback

## 9. 客户端状态机定义

前端连接状态建议如下：

```text
idle
connecting_ws
ws_active
ws_degraded
polling_active
resyncing
stopped
```

含义：

- `idle`：尚未订阅任何任务
- `connecting_ws`：正在建立连接
- `ws_active`：WebSocket 正常
- `ws_degraded`：短暂失联，等待重连
- `polling_active`：启用轮询兜底
- `resyncing`：重新连接成功后执行一次全量校准
- `stopped`：所有关注任务都已终态

## 10. 轮询启用规则

### 10.1 允许轮询的场景

只有以下情况允许启动轮询：

- WebSocket 建连失败
- WebSocket 意外断开且超过短暂重连窗口
- 页面从后台恢复，需要立即校准一次
- 某个任务收到异常状态，需要主动核对一次

### 10.2 不允许轮询的场景

- WebSocket 正常活动中
- 任务已终态
- 页面不可见且无强需求
- 用户离开相关页面且无任何任务被关注

## 11. 轮询策略定义

### 11.1 单任务详情页轮询

适用场景：

- 用户正在查看单个生成任务

策略：

- 前台可见：每 3 秒
- 页面后台：每 10 秒
- 连续失败 3 次后：退避到每 15 秒
- 收到终态：立即停止

### 11.2 列表页聚合轮询

适用场景：

- 工作台最近结果
- 项目页任务列表

策略：

- 前台可见：每 5 秒调用一次列表接口
- 页面后台：每 15 秒
- 只查运行中任务：`status in (billing_pending, queued, processing, cancelling)`
- 最大一次拉取 20 条任务

### 11.3 启动与停止规则

启动条件：

- 关注集合中存在非终态任务
- 且 `WebSocket` 当前不可用

停止条件：

- 所有关注任务进入终态
- 用户离开页面
- WebSocket 恢复且完成一次校准

## 12. 终态定义

以下状态视为终态：

- `completed`
- `failed`
- `cancelled`

账务终态补充：

- `settled`
- `refunded`

前端停止同步判断建议：

- 业务状态终态即可停止高频进度同步
- 如需展示退款完成提示，可保留一次低频校准直到账务进入终态

## 13. 去重与乱序保护

这是防止“轮询和 WebSocket 打架”的关键规则。

### 13.1 版本号优先

任务对象必须带 `version`。

前端更新规则：

- 新事件 `version` 小于本地版本：丢弃
- 新事件 `version` 等于本地版本：仅补充缺失字段
- 新事件 `version` 大于本地版本：覆盖

### 13.2 时间戳保护

如果特殊情况下没有 `version`，则退化为比较：

- `updated_at`

但不建议仅依赖时间戳，因为不同链路可能出现毫秒级碰撞。

### 13.3 事件去重

事件带 `event_id`。

前端应保留短期去重缓存，避免重连后重复事件造成重复提示。

## 14. 重连策略

### 14.1 WebSocket 重连节奏

建议指数退避：

- 第 1 次：1 秒
- 第 2 次：2 秒
- 第 3 次：5 秒
- 第 4 次：10 秒
- 第 5 次及以后：15 秒

每次重连加入随机抖动 `0-20%`。

### 14.2 重连窗口

WebSocket 断开后：

- 先进入 `ws_degraded`
- 在 5 秒内优先尝试重连
- 超过 5 秒仍未恢复，再启用轮询兜底

这样可以避免短时网络抖动就立刻切到轮询。

### 14.3 重连成功后

重连成功不能直接相信本地状态，必须：

1. 执行一次 `resync`
2. 调 `GET /api/v1/tasks/{id}` 或列表接口校准当前任务
3. 再关闭轮询兜底

## 15. 页面可见性策略

### 15.1 页面可见

- 保持 WebSocket
- 允许高频进度更新
- fallback 轮询使用前台频率

### 15.2 页面隐藏

- WebSocket 保持连接，但允许服务端心跳更低频
- 若进入轮询兜底，则自动降频
- 不允许后台每 3 秒持续打接口

### 15.3 页面重新激活

页面恢复前台时必须立即做一次状态校准：

- 单任务页调详情
- 列表页调列表

## 16. 服务端实现要求

### 16.1 推送来源

服务端推送只来自任务状态真正落库后的事件，不允许直接把供应商原始回调结果未经落库就推给前端。

正确顺序：

1. 更新数据库
2. 记录 `task_events`
3. 发布实时事件

### 16.2 心跳与保活

WebSocket 需要心跳机制：

- 服务端每 20-30 秒发一次 ping
- 客户端超时未收到心跳时视为失联

### 16.3 连接上限

每个用户应设置连接上限，避免同账号多标签页和异常脚本造成连接膨胀。

### 16.4 推送粒度

推送单位按用户，而不是按页面或组件：

- 频道：`user:{userId}:tasks`

这样前端多个页面可以共享一条连接。

## 17. 推荐的前端接入顺序

### 阶段一

- 任务创建后先只做详情查询
- 拉通任务状态 DTO

### 阶段二

- 接入 WebSocket
- 工作台和项目页共享任务事件流

### 阶段三

- 接入受控轮询 fallback
- 完成页面可见性与重连策略

### 阶段四

- 补齐监控、告警和事件去重

## 18. 监控与告警

必须监控：

- WebSocket 建连成功率
- WebSocket 平均在线时长
- 重连频率
- fallback 轮询触发率
- 单用户轮询 QPS
- 非终态任务平均停留时长
- 终态后仍被轮询的异常次数

需要告警：

- WebSocket 全局失败率突然升高
- fallback 轮询占比异常升高
- 同一任务在终态后仍被轮询超过 3 次
- 单用户连接数超限

## 19. 本项目明确开发结论

本项目的图片生成状态同步，采用以下强约束：

1. `WebSocket` 是唯一主通道。
2. HTTP 轮询只作为降级兜底，不作为常规主方案。
3. 前端必须有统一任务同步协调器，不允许组件各自轮询。
4. 列表页只能聚合轮询列表接口，不允许一任务一请求。
5. 任务必须带 `version`，前端按版本防乱序覆盖。
6. 任务终态后立即停止高频同步。
7. WebSocket 恢复后必须执行一次 `resync`，再关闭轮询。
