# 后端启动任务清单

## 1. 文档目标

本文基于当前已有的产品文档、后端技术方案、任务实时同步规范，整理出后端启动阶段的最小可执行任务清单。

目标不是一次性展开全部业务开发，而是明确：

- 第一阶段先做什么
- 为什么这样排顺序
- 每一步的产出是什么
- 哪些事情现在不要提前做

本文适用于后端正式开工前的工程搭建和基础链路落地。

## 2. 启动阶段总原则

后端第一步不应优先做：

- WebSocket 网关
- 真实 AI 供应商接入
- 支付接入
- 大量页面联调
- 各模块零散接口开发

后端第一步应优先做的是：

1. 搭建整体工程骨架
2. 落数据库 schema 基线
3. 打通最小任务主链路

原因很明确：

- `WebSocket` 建立在任务模型和任务事件之上
- 页面接口建立在统一 DTO 和数据库事实之上
- 支付、积分、任务、实时这些能力都需要稳定的服务边界和表结构

因此，启动阶段的核心不是“先让某个页面能跑”，而是“先让后端系统有稳定骨架和任务事实源”。

## 3. 第一阶段拆分为 7 个最小可开发动作

## 3.1 动作一：确定后端工程形态

### 目标

明确服务划分、仓库结构和公共包边界。

### 建议结构

```text
backend/
  apps/
    biz-api/
    ledger-service/
  packages/
    shared-types/
    shared-kernel/
```

### 本动作需要完成

- 确定采用双服务：
  - `biz-api`
  - `ledger-service`
- 确定是否使用 monorepo
- 确定公共类型和公共基础能力的存放位置

### 产出

- 后端仓库目录结构说明
- 服务边界说明
- 开发启动方式说明

### 注意事项

- 第一阶段只抽最小公共层，不要过度设计
- 不要一开始拆过多微服务

## 3.2 动作二：搭建 NestJS 基础骨架

### 目标

让两个后端服务可以独立启动，并具备一致的基础能力。

### 本动作需要完成

两个服务统一接入以下基础设施：

- 配置管理
- 环境变量加载
- 结构化日志
- 统一响应体
- 全局异常处理
- 健康检查
- Swagger/OpenAPI 入口

### 建议模块

每个服务至少建立：

- `app`
- `config`
- `common`
- `infra`

### 产出

- `biz-api` 可启动
- `ledger-service` 可启动
- 两个服务均有基础 health 接口
- 两个服务均有 Swagger 页面

### 验收标准

- 本地启动无报错
- 能读取 `.env`
- 健康检查返回成功
- 日志格式统一

## 3.3 动作三：初始化双数据库连接和 Prisma 基线

### 目标

让业务库和积分库都进入真正可迁移、可连接、可演进的状态。

### 本动作需要完成

- 确定数据库实例或数据库名
  - 业务库
  - 积分库
- 配置 Prisma
- 设计两套 schema 管理方式
- 打通 migration 流程

### 推荐做法

可采用两套 Prisma schema 或两套 client，重点是：

- 业务服务只直接操作业务库
- 积分服务只直接操作积分库
- 不允许跨服务直接访问对方数据库

### 产出

- 双库连接配置
- Prisma 初始化完成
- 首次 migration 可执行

### 验收标准

- 可以分别连接两个数据库
- migration 执行成功
- 本地可重建环境

## 3.4 动作四：先落第一批核心表，不求全量

### 目标

把最关键的数据事实先建起来，足够支撑认证、任务、积分主链路。

### 业务库第一批核心表

- `users`
- `auth_sessions`
- `verification_codes`
- `assets`
- `projects`
- `task_quotes`
- `generation_tasks`
- `task_inputs`
- `task_outputs`
- `task_events`

### 积分库第一批核心表

- `credit_accounts`
- `billing_tasks`
- `credit_transactions`
- `idempotency_keys`

### 特别要求

`generation_tasks` 必须第一批就包含以下字段：

- `module`
- `scene`
- `task_type`
- `project_id`
- `batch_id`
- `source_page`
- `version`

### 为什么必须现在就落这些字段

因为这些字段已经被后续文档依赖：

- 多模块并发任务同步规范
- 任务实时状态同步开发文档
- 模块级筛选与分发逻辑
- 乱序保护与事件版本控制

如果现在不进入数据库，后面会发生：

- DTO 返工
- WebSocket 事件返工
- 查询接口返工

### 产出

- 第一批数据库表
- 第一批索引
- 第一批枚举字段定义

### 验收标准

- 业务库核心任务表可插入任务数据
- 积分库核心账务表可插入账户与流水
- 任务表支持模块维度查询

## 3.5 动作五：定义统一 DTO 与枚举

### 目标

在接口开发前，先固定后端核心领域对象，避免后期反复重命名和返工。

### 必须优先定义的枚举

- `TaskModule`
- `TaskType`
- `TaskStatus`
- `BillingStatus`
- `AssetStatus`
- `ReviewStatus`

### 必须优先定义的 DTO

- `TaskSummaryDto`
- `TaskDetailDto`
- `TaskRealtimeEventDto`
- `CreateTaskRequestDto`
- `TaskEstimateRequestDto`
- `TaskEstimateResponseDto`

### 特别要求

任务 DTO 必须包含：

- `module`
- `scene`
- `task_type`
- `project_id`
- `batch_id`
- `source_page`
- `status`
- `billing_status`
- `progress`
- `stage`
- `updated_at`
- `version`

### 为什么先做 DTO

如果不先固定 DTO，会出现：

- 数据库一套命名
- HTTP 返回一套命名
- WebSocket 又一套命名
- 前端 store 再做一层转换

这会直接导致后续联调成本暴涨。

### 产出

- 统一的领域枚举
- 统一的任务 DTO
- 统一的错误码基础约定

### 验收标准

- HTTP 和 WebSocket 都能复用同一套任务字段定义
- 模块、项目、批次过滤字段已经进入 DTO

## 3.6 动作六：打通最小任务主链路骨架

### 目标

先跑通“可落库、可流转、可写事件”的最小任务闭环，不急着接真实 AI 服务。

### 本动作要打通的链路

1. 创建报价
2. 创建任务
3. 写入 `generation_tasks`
4. 写入 `task_events`
5. 调积分服务冻结积分占位
6. 更新任务状态
7. 任务版本号递增

### 当前阶段可以接受的简化

- AI 供应商可先用 mock worker 代替
- 结果图可先用占位生成
- 不要求真实出图能力立即可用

### 当前阶段必须真实存在的能力

- 任务真实落库
- 任务状态真实更新
- 事件真实写库
- 冻结调用链路真实存在

### 为什么先做这个

因为它是下面这些能力的共同前提：

- WebSocket 推送
- 项目页展示
- 最近结果展示
- 任务详情页
- 积分冻结与退款补偿

### 产出

- 最小任务服务
- 最小积分冻结调用
- 最小任务事件记录

### 验收标准

- 可创建任务
- 任务状态可从 `created` 流转到 `queued/processing/completed/failed`
- `task_events` 中能看到事件历史
- `version` 每次更新递增

## 3.7 动作七：最后再做实时链路

### 目标

在任务事实源和状态流转稳定后，再接入 WebSocket 和 fallback 轮询。

### 本动作需要完成

- `POST /api/v1/realtime/token`
- `GET /api/v1/ws`
- 任务事件发布器
- WebSocket 网关
- fallback 查询接口能力

### 为什么放最后

因为 WebSocket 不是状态来源，它只是状态分发通道。

如果先做实时链路，再补任务表和状态机，通常会出现：

- 推送字段变化频繁
- 版本控制逻辑返工
- 前端订阅逻辑反复调整

### 实施前提

必须先满足：

- 任务主链路已可运行
- `task_events` 已有真实事件来源
- `version` 和 `updated_at` 已经稳定

### 产出

- 单主连接实时链路
- 多模块任务分发能力
- fallback 轮询兜底能力

### 验收标准

- WebSocket 推送真实落库事件
- 断线可恢复
- fallback 不会重复建立多套轮询

## 4. 启动阶段的推荐顺序

建议严格按以下顺序推进：

1. 工程形态
2. 服务骨架
3. 双库连接
4. 第一批核心表
5. DTO 与枚举
6. 最小任务主链路
7. WebSocket 与实时同步

这个顺序的核心逻辑是：

- 先有系统容器
- 再有数据事实
- 再有状态流转
- 最后才有实时分发

## 5. 当前阶段明确不要提前做的事情

以下事项不建议在启动阶段提前做：

- 真实 AI 图片供应商接入
- 支付渠道正式接入
- 企业版复杂权限体系
- 全量后台运营配置系统
- 多页面全面联调
- 前端全局任务中心完整实现

原因：

- 这些都依赖任务主链路和数据模型稳定
- 现在提前做，只会导致返工

## 6. 启动阶段建议的分工方式

### 后端负责人

负责：

- 工程骨架
- 双服务划分
- 公共基础设施
- 数据库 schema 基线

### 业务后端开发

负责：

- 认证基础链路
- 任务主链路
- 任务事件落库

### 积分服务开发

负责：

- 账户表
- 冻结表
- 流水表
- 幂等机制基础实现

### 前端配合方

当前阶段只需要：

- 确认 DTO 字段
- 预留接入位

不需要现在就展开全量实时联调。

## 7. 启动阶段里程碑

### 里程碑一：服务可启动

标志：

- 双服务都能跑起来
- 双库都能连接

### 里程碑二：核心表可落库

标志：

- 任务表和积分表建成
- migration 可重复执行

### 里程碑三：任务主链路打通

标志：

- 可创建任务
- 可写任务事件
- 可做冻结占位

### 里程碑四：实时能力可接入

标志：

- WebSocket 开始推送真实事件
- fallback 轮询有稳定事实源

## 8. 一句话结论

后端启动阶段最正确的第一步，不是先做 WebSocket，也不是先做零散业务接口，而是：

- 先搭双服务后端骨架
- 同步落第一批双库 schema
- 再打通最小任务主链路

只有这三步先成立，后续实时同步、多模块并发、积分一致性和前端联调才不会反复返工。
