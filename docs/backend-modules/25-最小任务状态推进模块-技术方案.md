# 最小任务状态推进模块技术方案
## 1. 模块目标

本模块的目标，是在已经完成真实 Prisma 写库和接口验收的基础上，补齐任务中心最小可用的状态推进能力。

当前系统虽然已经具备：

- 任务报价创建
- 任务主表写入
- 任务事件写入
- 列表、详情、事件查询

但任务状态仍然长期停留在 `queued`，这会直接阻塞后续：

- 全局任务中心
- WebSocket 实时推送
- 多模块任务并发展示
- 前端状态同步

因此这一阶段优先补“状态源”，而不是补“同步层”。

## 2. 设计范围

本模块纳入范围：

- 任务状态推进接口
- 最小状态机规则
- 状态流转事件追加
- 任务版本号递增
- 生命周期验收脚本

本模块暂不纳入范围：

- 自动调度器
- Worker 异步消费
- 真实图片生成回调
- WebSocket 推送广播

## 3. 状态机范围

当前仅支持最小链路：

- `queued -> processing`
- `queued -> failed`
- `processing -> completed`
- `processing -> failed`

终态定义：

- `completed`
- `failed`

终态后不允许继续推进，避免前端状态回滚和重复结算。

## 4. 接口设计

新增接口：

- `POST /api/v1/tasks/{id}/status`

请求体：

- `status`
- `progress`
- `stage`
- `error_code`
- `error_message`
- `settled_credits`

接口职责：

- 校验目标状态是否合法
- 校验当前状态是否允许转移
- 更新任务主表
- 递增版本号
- 追加状态事件

## 5. 事件设计

状态变更时，追加以下事件：

- `processing` -> `task.updated`
- `completed` -> `task.completed`
- `failed` -> `task.failed`

事件中补齐：

- `from_status`
- `to_status`

这样前端后续无论走轮询还是 WebSocket，都可以基于事件顺序安全更新本地状态。

## 6. 状态字段更新规则

### 6.1 `processing`

- `status = processing`
- `progress` 至少大于 0
- `stage` 默认 `processing`
- `version + 1`

### 6.2 `completed`

- `status = completed`
- `progress = 100`
- `stage = completed`
- `settled_credits` 默认等于 `estimated_credits`
- `completed_at = now`
- `version + 1`

### 6.3 `failed`

- `status = failed`
- `stage = failed`
- `error_code` 默认为 `TASK_FAILED`
- `error_message` 默认为 `Task failed`
- `version + 1`

## 7. 验收标准

满足以下条件，才算模块通过：

- 可通过接口将任务从 `queued` 推到 `processing`
- 可通过接口将任务从 `processing` 推到 `completed`
- 每次推进后 `version` 递增
- 每次推进后 `updated_at` 更新
- 完成态返回 `progress = 100`
- 事件流按顺序包含 `task.created -> task.updated -> task.completed`
- 事件中 `from_status / to_status` 正确
- 非法状态流转返回明确错误

## 8. 下一步建议

本模块完成后，下一步才适合进入：

- 任务实时同步模块

也就是把当前已经稳定的：

- 任务主表状态
- 任务版本号
- 状态事件流

接入单主 WebSocket 和全局任务中心。

## 9. 结论

本模块不是“多做一个接口”，而是把任务系统从“只有创建态”推进为“有完整最小生命周期”。这是后续实时同步和多模块任务中心的必要前提。
