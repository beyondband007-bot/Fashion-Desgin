# 最小任务主链路模块开发归纳

## 1. 本次开发目标

本次开发的目标是从“只有框架和类型”进入“有真实任务动作”的阶段，先做出最小任务主链路。

## 2. 本次实际完成内容

### 2.1 新增共享 HTTP 工具

新增：

- `backend/packages/shared-kernel/src/http/json.ts`

当前提供：

- JSON body 读取
- JSON 响应输出

### 2.2 新增共享 ID 工具

新增：

- `backend/packages/shared-kernel/src/utils/id.ts`

用于当前阶段生成任务、事件、报价的临时 ID。

### 2.3 新增任务模块代码

新增目录与文件：

- `controllers/task.controller.ts`
- `services/task.service.ts`
- `services/ledger.client.ts`
- `store/task.store.ts`

### 2.4 新增任务接口

当前已挂载接口：

- `POST /api/v1/tasks/estimate`
- `POST /api/v1/tasks`
- `GET /api/v1/tasks`
- `GET /api/v1/tasks/{id}`
- `GET /api/v1/tasks/{id}/events`

### 2.5 首次打通任务主流程

当前已经可以完成：

- 生成报价
- 创建任务
- 生成任务摘要
- 生成 `task.created` 事件
- 返回冻结积分占位结果

### 2.6 当前存储方式

当前采用内存态 store：

- 任务存在 `taskStore`
- 报价存在 `taskStore`
- 事件存在 `taskStore`

这一步的目的不是替代数据库，而是先验证主链路结构。

### 2.7 新增文档

新增：

- 技术方案文档
- 本开发归纳文档

## 3. 当前状态判断

当前后端已经从“只有工程结构和 schema”进入“能够响应任务接口”的阶段。

这是一个关键分界点，因为后续前端、实时、积分、项目页面都终于有了真实业务对象可对接。

## 4. 本次开发的关键价值

这一步最重要的价值不是接口数量，而是第一次把以下东西串起来了：

- DTO
- 任务 store
- 控制器
- 事件记录
- 账务冻结占位

也就是说，任务已经从“文档概念”变成了“代码中的真实流转对象”。

## 5. 当前已知限制

- 任务还没有落数据库
- 事件还没有落数据库
- 没有 worker 驱动后续状态变更
- 没有真实积分服务 HTTP 调用
- 没有 WebSocket 推送
- 没有查询过滤能力

## 6. 下一步建议

下一步建议优先开发：

- 任务持久化与 repository 模块

原因：

- 当前接口已经成型
- 现在最大短板是任务数据还不持久
- 在持久化之前做 WebSocket，推送源仍然不稳定

## 7. 本次开发结论

这次开发完成的是“最小任务主链路模块”。它让后端第一次具备了任务预估、任务创建、任务查询和任务事件记录能力，是后续进入持久化和实时同步的真正起点。
